# Phase 2.2 — Verification Gate & Containment

**Subsystem:** `evolzen.containment`
**Code:** `src/evolzen/containment/`

## Goal

Provide the execution boundary for all agent-generated and synthesized code, and the promotion
boundary for new capability packages. Exact replay/intervention checks are reused from Phase 1.4.
The security design is fail-closed: static default-deny policy is authoritative, while
behavior-sensitive governance may tighten access but may not bypass the static policy.

The `Sandbox` protocol can be developed early, but a real containment claim requires a deployed
Firecracker/gVisor-backed executor and target-host acceptance tests. The interface alone is not a
security result.

## What you build

- capability-scoped default-deny policy;
- hardware-isolated backend integration;
- resource, filesystem, network, subprocess, syscall, and credential controls;
- tamper-evident action and governance logging;
- evaluator separation and deterministic recovery; and
- deliberate violation tests for kill-switch latency, cleanup, rollback, and restart.

## Success metric

Interface, backend, and target-host threat-model tests each pass: no unlogged action, no unbounded
resource use, fail-closed denial, bounded kill-switch latency, clean recovery, and preserved audit
logs. The report states which layer was actually tested.

## Citations

CORAL (arXiv:2604.01658), Sidik & Rokach (arXiv:2604.11839), and *Safety Must Precede the
Deployment of Open-Ended AI* (arXiv:2502.04512) are threat-model and safeguard references. The
security of a specific backend on the stated hardware is **untested** until deployment validation.
