# Phase 2.2 — Verification Gate & Containment

**Subsystem:** `evolzen.containment`
**Code:** `src/evolzen/containment/`

## Goal

Provide the execution boundary for all agent-generated and synthesized code, and the promotion
boundary for new capability packages. Exact replay/intervention checks are reused from Phase 1.4.
The security design is fail-closed: static default-deny policy is authoritative, while
behavior-sensitive governance may tighten access but may not bypass the static policy.

The `Sandbox` protocol can be developed early, but a real containment claim requires a deployed
Firecracker/gVisor-backed executor and target-host acceptance tests. The interface alone is not a
security result.

## What you build

- capability-scoped default-deny policy;
- hardware-isolated backend integration;
- resource, filesystem, network, subprocess, syscall, and credential controls;
- tamper-evident action and governance logging;
- evaluator separation and deterministic recovery; and
- deliberate violation tests for kill-switch latency, cleanup, rollback, and restart.

## Success metric

Interface, backend, and target-host threat-model tests each pass: no unlogged action, no unbounded
resource use, fail-closed denial, bounded kill-switch latency, clean recovery, and preserved audit
logs. The report states which layer was actually tested.

## Citations

- **Peer-reviewed systems conference:** Agache et al. (*Firecracker*, *USENIX NSDI* 2020) for KVM-backed microVM isolation (~5 MB memory overhead, millisecond startup, minimal virtio device model).
- **Preprints:** CORAL (`arXiv:2604.01658`), Sidik & Rokach (`arXiv:2604.11839`), and *Safety Must Precede the Deployment of Open-Ended AI* (`arXiv:2502.04512`).

The security of a specific backend on the stated hardware is **untested** until deployment validation.

## Research context & breakthroughs

- **MicroVM vs. shared-kernel containers:** Firecracker (*USENIX NSDI*, 2020) established that dedicated KVM virtualization with a Rust VMM and stripped legacy hardware avoids the shared-kernel attack surface of containers while preserving lightweight startup—justifying why `SECURITY.md` forbids treating plain subprocesses or shared-kernel containers as a final containment boundary for `evolzen.agents` / `evolzen.exploration` code execution.
- **Fail-closed learned governance:** Recent agent-governance proposals (`arXiv:2604.11839`) motivate dynamic risk tightening strictly inside static default-deny capability bounds (`CapabilityGovernor`).

## Codebase progress match

- **Governance (`src/evolzen/containment/governance.py`):** Implemented `CapabilityGovernor` supporting dynamic tightening via `record_violation()` (immediate capability revocation and violation logging), capability verification gating (`verify_capability_package()` enforcing fail-closed `verified_containment` and boundary invariants), audit trail export (`export_audit_trail()`), and cryptographic tamper-evident SHA-256 hash chaining (`audit_hash()`). Fully tested across 8 unit tests in `tests/containment/test_governance.py`.
- **Sandbox (`src/evolzen/containment/sandbox.py`):** Implemented runtime-checkable `Sandbox` protocol and `GVisorSandbox` driver using `runsc` with `--net=none`, memory limit ceiling, wall-time timeouts, structured JSON `(Emission, State)` return channels (`ExecutionResult.get_json_output()`), and fail-closed denial (strictly raising `RuntimeError` when `runsc` is unavailable without bare subprocess fallback). Implemented `is_gvisor_available()` host probe.
- **Test Harness & Mocking (`tests/containment/conftest.py` & `tests/containment/test_sandbox.py`):** Implemented `MockSandbox` test fixture providing hermetic sandbox simulation with invocation history tracking, timeout/OOM simulation, and deterministic structured output extraction. Verified across 21 unit tests covering frozen `ExecutionResult`, JSON decoding, security flags, fail-closed absence handling, and mocked/live execution.
- **Configuration (`src/evolzen/config.py` & `configs/containment.yaml`):** Implemented `ContainmentSettings` with `backend`, `runsc_path`, `default_timeout_seconds`, `default_resource_ceiling_mb`, and `enforce_containment`.
- **Open cross-phase alignment items:**
  - Wire `CapabilityGovernor` to `SocialSandboxEngine._handle_register_capability` and `WorldAgentState`, linking `GovernanceEvent` records with `TransitionLogStore`.
  - Wire `Verifier` (Phase 1.4) and `SocialSandboxEngine` (Phase 1.1) to execute untrusted code through `Sandbox` / `GVisorSandbox` (or `MockSandbox` in CI). Live target-host security remains **untested** until hardware deployment validation on Linux hosts with `runsc` installed.
