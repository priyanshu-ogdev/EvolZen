    Phase 0 — The Foreground (Completed Baseline Scaffold)

    Status note: Phase 0 scaffolding is complete and superseded by active subsystem work. Three baselines now have tested implementations beyond Phase 0 stubs: the persistent social sandbox environment (Phase 1.1: evolzen.environment, evolzen.schemas.world, and evolzen.storage.transition_log), the developmental numerical agent core (Phase 1.2 numerical baseline: evolzen.agents.development and evolzen.schemas.development), and the growing rule library (Phase 1.5: evolzen.library and evolzen.schemas.library). Empirical long-horizon runs, Phase 1.1 hardening, LLM/QD population loops, downstream subsystems (Phases 1.3–1.4, 2.1–2.5), and hardware-isolated sandboxing remain pending. The checklist below records the initial foreground engineering gates.

    What Phase 0 is

    Every research phase (1.1 through 2.4-2.5) assumes a working, documented, dependency-locked codebase to build inside. Phase 0 produces that codebase. It sits in front of the numbered research phases — hence "foreground" — and is intentionally free of research content: no trained models, no environment logic, no agent behavior.

    What "done" means for Phase 0

    • [x] One pyproject.toml, one package (evolzen), one lockfile — no workspace, no artificial multi-package split (see ADR 0001).
    • [x] Nine subsystem folders under src/evolzen/, named exactly what the PRD calls them, each with its own README.md explaining what belongs there, its success metric, and how to build it.
    • [x] Shared schemas (Transition, DriveVector, Manual) live in evolzen.schemas so no two subsystems can silently drift onto incompatible representations of the same data.
    • [x] Base dependencies install and pass tests on a CPU-only machine; GPU-only packages are an opt-in extra (see ADR 0002).
    • [x] tests/ mirrors src/evolzen/ exactly.
    • [x] CI runs lint, type-check, and test on every push, path-filtered per subsystem.
    • [x] docs/ contains a complete PRD, a complete ARCHITECTURE.md, one doc per phase, ADRs, and a dependency-stack rationale — a 1:1 mapping between "a phase in the plan" and "a place to read about it and a place to implement it."

    What Phase 0 explicitly does not do

    Historical boundary: The items below record what the Phase 0 foreground scaffold omitted before subsystem implementations began. Phase 1.1 (evolzen.environment) now implements the persistent social-sandbox baseline (with hardening and empirical pilots still pending), while hardware-isolated sandboxing and downstream research phases remain separate work.

    • It did not implement the persistent world engine — Phase 1.1 owned the concrete world state, growth categories, replay semantics, and domain-specific action vocabulary (now implemented at baseline in evolzen.environment, evolzen.schemas.world, and evolzen.storage.transition_log).
    • It does not pin exact dependency versions — pyproject.toml specifies ranges; uv lock --upgrade resolves current-stable versions periodically.
    • It does not stand up the hardware-isolated sandboxing (Firecracker/gVisor) — that's infrastructure, not a Python dependency.
    • It did not include any actual research logic — every function in Phase 0 had either a minimal, honestly-trivial implementation or raised NotImplementedError pointing at the phase doc specifying what should replace it (downstream stubs in Phases 1.2–1.4 and 2.1–2.5 still follow this convention).

    Owning a subsystem

    If you're the first to implement a stub past NotImplementedError: 1. Read the subsystem's README.md and the linked doc in docs/phases/. 2. Check docs/research/literature-review.md for the citation backing its design. 3. Replace the stub, keep the type signature stable if at all possible — other subsystems may already import it. 4. Add or extend the test in the matching tests/<subsystem>/ file.
